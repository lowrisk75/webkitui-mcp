# WKWebView capability ceiling for embedders, macOS 15 → macOS 27

Date: 2026-09-09

Question: Do the five capability statements this product is about to publish about WKWebView on macOS 15 through macOS 27 survive contact with Apple's shipping headers, WebKit source, and Apple's own privacy text?

Primary evidence base for this note, unless a URL is given inline: the **macOS 27.0 SDK shipped in Xcode-beta on this machine**, read 2026-09-09 at
`/Applications/Xcode-beta.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX27.0.sdk/System/Library/Frameworks/WebKit.framework/` — public `Headers/` plus `Modules/WebKit.swiftmodule/arm64e-apple-macos.swiftinterface`. This is the authoritative statement of what is *public* API; `github.com/WebKit/WebKit` `main` (read 2026-09-09) is used for SPI and implementation.

---

## Verdict

Statement 1 is the one that must not ship as written: it is **wrong on its central claim** — there are at least three non-injection routes to per-subresource and XHR visibility, one of which (`WKWebsiteDataStore.proxyConfigurations`) is public API that Apple's own DTS engineers recommend for exactly this purpose, and another of which (`WKWebExtension` hosting an extension with the `webRequest` permission) is public API sitting on WebKit's implemented, observation-only `browser.webRequest` event set — no blocking and no headers, but URLs, methods, resource types, and status codes for `xmlhttprequest` and `websocket` loads, from outside the page's reach. Statements 2 and 4 survive with tightening: the main-frame status cast is real but silent on redirect status codes and absent on back/forward-cache and same-document navigations, and console output still has no public API on macOS 27 — though a `_webView:didReceiveConsoleLogForTesting:` SPI appeared in macOS 26.4. Statement 3 is materially misdescribed: the default is correct, but Apple never says "hashed prefix", names **Apple itself and Google** (and Tencent for China-mainland *or Hong Kong* regions) as recipients, and Apple's current legal text says Google *may log your IP address* — the "Apple proxies it" story is press reporting of a WebKit engineer's tweet, not an Apple statement.

---

## Statement by statement

### 1. "WebKit exposes no API for inspecting individual subresource or XHR requests to an embedder, and the only route would be patching `fetch` and `XMLHttpRequest` inside the page"

**Claim as written:** no API exists; in-page monkey-patching is the only route; the site can observe and falsify it.

**Evidence.**

*Ruled out — these genuinely do not do it:*

- **`WKURLSchemeHandler`** — EXTERNAL-PRIMARY, definitive. `WKWebViewConfiguration.h` (macOS 27.0 SDK, read 2026-09-09) on `setURLSchemeHandler:forURLScheme:`: *"An exception will be thrown if you try to register a URL scheme handler for a URL scheme that WebKit handles internally. You can use `+[WKWebView handlesURLScheme:]` to check the availability of a given URL scheme."* Apple's doc is blunter (<https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/seturlschemehandler(_:forurlscheme:)>, read 2026-09-09): *"It is a programmer error to register a handler for a scheme WebKit already handles, such as https, and this method raises an `invalidArgumentException` if you try to do so."* The implementation in `Source/WebKit/UIProcess/API/Cocoa/WKWebViewConfiguration.mm` (read 2026-09-09) raises `NSInvalidArgumentException` with *"'%@' is a URL scheme that WKWebView handles natively"*. So this cannot see ordinary page traffic. Available since macOS 10.13.
- **`WKNavigationDelegate`** — EXTERNAL-PRIMARY. `WKNavigationDelegate.h` (macOS 27.0 SDK). Every callback is navigation-scoped. `decidePolicyForNavigationResponse:` fires for main-frame *and* subframe navigations (`WKNavigationResponse.isForMainFrame` distinguishes them) but never for images, scripts, stylesheets, `fetch`, or `XMLHttpRequest`. Confirmed by Apple DTS in <https://developer.apple.com/forums/thread/808093> (read 2026-09-09): the developer's rebuttal — *"the `webView(_:decidePolicyFor:preferences:decisionHandler:)` method only helps intercept navigation-level URL loads, whereas AJAX/XHR requests happen internally via JavaScript and don't trigger navigation actions"* — was accepted by the engineer, who then pivoted to the proxy answer below.
- **`NSURLProtocol`** — EXTERNAL-PRIMARY. This is a known, still-open WebKit bug: <https://bugs.webkit.org/show_bug.cgi?id=138169>, *"WKWebView does not support NSURLProtocol-style interception of http or https"*, filed 2014-10-29, status **NEW** as of its most recent activity (read 2026-09-09). WKWebView loads run in a separate Networking process, so an in-app `URLProtocol` registration is never consulted. Brady Eidson (WebKit) notes in that bug that even the old UIWebView behaviour *"does not actually allow for intervention in all traffic. Notably, most traffic for video and audio assets does not get captured as it happens in mediaserverd, not the host process."* Maciej Stachowiak's reply in the same bug — *"For folks following this bug, who would consider it sufficient to have a way to define per-app or per-WKWebView proxy setting?"* — is the origin of `proxyConfigurations` below. Note also that `WKProcessPool` is **deprecated** as of macOS 26 (<https://webkit.org/blog/17333/webkit-features-in-safari-26-0/>, read 2026-09-09), so the old private-protocol trick has no future. The `WKBrowsingContextController registerSchemeForCustomProtocol:` workaround is UNAVAILABLE for verification — not located in current WebKit source; treat as gone.
- **Web Inspector / `WKWebView.isInspectable`** — EXTERNAL-PRIMARY, and the cost is the decisive part. `WKWebView.h` (macOS 27.0 SDK): *"Controls whether this WKWebView is inspectable in Web Inspector. The default value is NO."* — `macos(13.3), ios(16.4)`. Apple's doc (<https://developer.apple.com/documentation/webkit/wkwebview/isinspectable>, read 2026-09-09) is explicit that this is a *Safari-attaches-to-you* switch: *"Set to `true` at any point in the view's lifetime to allow Safari Web Inspector access to inspect the view's content. Then, select your view in Safari's Develop menu for either your computer or an attached device to inspect it."* Background: <https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/> (read 2026-09-09). **There is no public API to read network activity through it**, and no SPI either: `_WKInspector` (`Source/WebKit/UIProcess/API/Cocoa/_WKInspector.h`, read 2026-09-09) exposes only `connect`, `attach`/`detach`, `hide`, `showMainResourceForFrame:`, `togglePageProfiling`, `toggleElementSelection`, `printErrorToConsole:` — a window/lifecycle controller, no network data and no protocol-message channel. The predecessor `WKWebView._allowsRemoteInspection` is deprecated in favour of `inspectable` (`macos(10.10, 13.3)`). Driving the protocol would mean speaking Remote Web Inspector over `webinspectord`; the gating entitlement is `com.apple.webinspector.allow`, which Apple DTS (Quinn) describes in <https://developer.apple.com/forums/thread/745027> (read 2026-09-09) as *"a restricted entitlement and thus must be authorised by a provisioning profile. However, I can't see any way to create a profile with that in its allowlist."* **Cost: unobtainable for an App Store or Developer ID build.** Related dead ends: `safaridriver` automates Safari only (<https://developer.apple.com/documentation/safari-developer-tools/webdriver>), Cocoa has no public automation API (only SPI `_WKAutomationSession` and `WKWebViewConfiguration._isControlledByAutomation`, unlike WebKitGTK/WPE's public `WebKitAutomationSession`), and WebDriver has no Network-domain command set anyway. Safari 27's Web Inspector *did* gain "Network tab shows complete redirect chains" (<https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/>, read 2026-09-09) — a human-facing UI feature, not an embedder API.
- **`WKWebsiteDataStore` data APIs** — EXTERNAL-PRIMARY. `WKWebsiteDataStore.h` / `WKWebsiteDataRecord.h` (macOS 27.0 SDK) expose per-origin *stored data* records (cache, cookies, storage, and new in macOS 26 `WKWebsiteDataTypeScreenTime`) and, new in macOS 26, `fetchDataOfTypes:` / `restoreData:`. These are aggregate storage inventories after the fact, not a request stream.
- **`WKContentRuleList`** — EXTERNAL-PRIMARY, and this is the interesting near-miss. Content rule lists *do* match subresource loads by `resource-type`, and WebKit has had a `notify` action type since 2017 (<https://bugs.webkit.org/show_bug.cgi?id=177013>, r222602, read 2026-09-09). But **no delivery path is public**: grepping every public header in the macOS 27.0 SDK finds `WKContentRuleList`, `WKContentRuleListStore`, and exactly one new observation crumb — `WKNavigationAction.isContentRuleListRedirect`, `API_AVAILABLE(macos(26.0))`. The actual notification callbacks live in SPI: `_webView:URL:contentRuleListIdentifiers:notifications:` (`macos(10.13.4)`) and `_webView:contentRuleListWithIdentifier:performedAction:forURL:` (`macos(10.15)`), both in `Source/WebKit/UIProcess/API/Cocoa/WKNavigationDelegatePrivate.h` (read 2026-09-09).

*Rules the claim out — these do see subresources and XHR:*

- **`WKWebsiteDataStore.proxyConfigurations` — public API, macOS 14.0+, and Apple's own recommended answer.** EXTERNAL-PRIMARY. Present in the macOS 27.0 SDK's Swift interface as `@available(macOS 14.0, iOS 17.0, visionOS 1.0, *) public var proxyConfigurations: [Network.ProxyConfiguration]`; documented at <https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1> (read 2026-09-09). In <https://developer.apple.com/forums/thread/808093> (read 2026-09-09) the Apple DTS engineer answers the AJAX-interception question with: *"A colleague mentioned that you should be able to do this by applying a custom proxy to the web view. See the proxyConfigurations property on WKWebsiteDataStore. This will allow you to see the contents of HTTP requests going through your WKWebView."* Apple demonstrates the pattern itself in <https://developer.apple.com/videos/play/wwdc2023/10002/> ("Ready, set, relay", read 2026-09-09): *"The same proxy configuration object can also be used to proxy connections made in a WebKit view! … Now, this Webkit view is also sending its traffic through the relay."* This is the only public route that sees **every** load — main frame, subresources, XHR/fetch, media — because it operates below WebKit entirely, at the Networking process's transport. Costs, and they are substantial: (a) as stated in the forum thread, HTTPS requires TLS inspection; without a trusted root you observe only `CONNECT host:443` — hostname, port, timing, byte counts, no paths, methods, headers, or bodies; (b) the header warns *"Changing the proxy configurations might interupt current networking operations in any WKWebView that use this WKWebsiteDataStore, so it is encouraged to finish setting the proxy configurations before starting any page loads"*; (c) **two unverified gates before committing to this route** — whether a sandboxed App Store macOS app can install a system-trusted root CA without user admin authentication (almost certainly not), and which of `com.apple.security.network.server` / `.client` the local listener needs. These are deployment costs, not an absence of API.
- **`WKWebExtension` hosting an extension with the `webRequest` permission — public API, macOS 15.4+.** EXTERNAL-PRIMARY. `WKWebExtensionPermission.h` (macOS 27.0 SDK) declares, at `API_AVAILABLE(macos(15.4), ios(18.4), visionos(2.4))`: *"The `webRequest` permission requests access to the `browser.webRequest` APIs."* — plus `declarativeNetRequest`, `declarativeNetRequestFeedback`, `declarativeNetRequestWithHostAccess`, and `webNavigation`. WebKit implements the observational event set: `Source/WebKit/WebProcess/Extensions/Interfaces/WebExtensionAPIWebRequest.idl` (read 2026-09-09 via `gh api`) declares `onBeforeRequest`, `onBeforeSendHeaders`, `onSendHeaders`, `onHeadersReceived`, `onAuthRequired`, `onBeforeRedirect`, `onResponseStarted`, `onCompleted`, `onErrorOccurred`, over a `WebExtensionWebRequestResourceType` enum that explicitly includes `"xmlhttprequest"` and `"websocket"`. It is fed by the host app's own web views: `Source/WebKit/UIProcess/Extensions/WebExtensionController.h` declares `resourceLoadDidSendRequest`, `resourceLoadDidPerformHTTPRedirection`, `resourceLoadDidReceiveChallenge`, `resourceLoadDidReceiveResponse`, `resourceLoadDidCompleteWithError`, and `hasPermissionToSendWebRequestEvent(WebExtensionTab*, const URL&, const ResourceLoadInfo&)` — i.e. **`browser.webRequest` is a permission-gated view of the same internal resource-load observer that `_WKResourceLoadDelegate` exposes as SPI.** The host app does **not** need a separate app-extension target: `WKWebExtension.extensionWithResourceBaseURL:` (macOS 27.0 SDK header, `macos(15.4)`) loads an extension from a plain directory in the app's own bundle, and the extension reports back through `webExtensionController:sendMessage:toApplicationWithIdentifier:...` or `connectUsingMessagePort:` (`WKWebExtensionControllerDelegate.h`, macOS 27.0 SDK). The extension's JavaScript runs in the extension's own privileged world, not the page's, so the *page* cannot patch or observe it — precisely the property statement 1 says is unobtainable. **Do not over-promise what it yields.** Apple's compatibility documentation (<https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility>, read 2026-09-09) states: *"Blocking requests not supported"*, *"`BlockingResponse` not supported"*, *"`opt_extraInfoSpec` not supported for any of the events"*, and, for webRequest, *"Not supported in iOS"* — which contradicts the `ios(18.4)` availability on the permission constant, so treat it as macOS-only until tested. No `opt_extraInfoSpec` means **no `requestHeaders` / `responseHeaders` in practice**, even though the IDL's details dictionary declares those keys. Realistic yield: URL, method, resource type, frame/tab identity, redirect target, status code, timing — observation, not interception, and without headers. `declarativeNetRequest` is the modification path (and the sole focus of <https://developer.apple.com/videos/play/wwdc2026/216/>, "Create web extensions for Safari", WWDC26), but `declarativeNetRequestFeedback` reports only *matched rules*, not a request stream, so it is not a substitute observer. Setup cost is real: author a manifest and background script, bundle them, implement `WKWebExtensionTab` and `WKWebExtensionWindow`, load a `WKWebExtensionContext`, grant `webRequest` plus host permissions, bridge events back to native.
- **`_WKResourceLoadDelegate` — SPI, macOS 11.0+, and it is exactly what the statement says does not exist.** EXTERNAL-PRIMARY (WebKit source), but SPI. `Source/WebKit/UIProcess/API/Cocoa/WKWebViewPrivate.h` declares `@property (nonatomic, weak, setter=_setResourceLoadDelegate:) id <_WKResourceLoadDelegate> _resourceLoadDelegate WK_API_AVAILABLE(macos(11.0), ios(14.0));` and `_WKResourceLoadDelegate.h` (read 2026-09-09) declares `resourceLoad:didSendRequest:`, `resourceLoad:didPerformHTTPRedirection:newRequest:`, `resourceLoad:didReceiveChallenge:`, `resourceLoad:didReceiveResponse:`, `resourceLoad:didCompleteWithError:response:`. `_WKResourceLoadInfo.h` carries `resourceLoadID`, `frame`, `parentFrame`, `documentID`, `originalURL`, `originalHTTPMethod`, `eventTimestamp`, `loadedFromCache`, and a `resourceType` enum including `_WKResourceLoadInfoResourceTypeFetch` and `_WKResourceLoadInfoResourceTypeXMLHTTPRequest`. Also SPI: `WKWebView._networkRequestsInProgress`. **This is private API.** It is absent from the macOS 27.0 SDK (grepping every public header for `resourceLoad` returns only the deprecated WebKitLegacy `WebResourceLoadDelegate`). Using it means re-declaring headers, accepting App Store guideline 2.5.1 risk, and accepting silent breakage between OS releases.

*Historical footnote worth knowing:* the capability existed publicly in the previous engine. `WebResourceLoadDelegate.h` is still in the macOS 27.0 SDK, with `webView:resource:willSendRequest:redirectResponse:fromDataSource:` and `didReceiveResponse:`. It belongs to the deprecated WebKitLegacy `WebView`, not `WKWebView`. The modern engine removed the public per-resource hook rather than never having had one.

*Nothing at WWDC 2025 or WWDC 2026 changed this.* Diffing the macOS 27.0 SDK for `macos(26` and `macos(27` availability (2026-09-09) turns up no resource-load observation API. What macOS 27 did add is telling in the other direction: `WKWebpagePreferences.overrideReferrer` — *"Used to apply a custom `referer` header to all resource loads in the frame for this navigation"* — lets an embedder *influence* every subresource load while still not being told about any of them.

**Verdict: REFUTED**

**Correction to publish.** Replace with something like: *"WKWebView has no public per-request delegate for subresource, `fetch`, or `XHR` loads — the modern engine dropped the per-resource hook the deprecated WebKitLegacy `WebView` had, and `WKURLSchemeHandler` is barred from `http`/`https`, `NSURLProtocol` is out of process, `WKContentRuleList` notifications are SPI-only, and `isInspectable` only lets a human attach Safari's Web Inspector. Three routes do work without touching page JavaScript: routing the data store through a proxy you control (`WKWebsiteDataStore.proxyConfigurations`, macOS 14+, public, and Apple DTS's own recommendation — needs TLS inspection to see anything above the CONNECT hostname); hosting a bundled web extension with the `webRequest` permission (`WKWebExtension`, macOS 15.4+, public, observational `browser.webRequest` events covering `xmlhttprequest` and `websocket` — but no blocking and no request or response headers, per Apple's compatibility documentation); and `_WKResourceLoadDelegate`, which does exactly this and has since macOS 11 but is private API and therefore not shippable. Patching `fetch` and `XMLHttpRequest` in the page is the route the page can detect and lie to; it is not the only route."* Do not claim "no API" and do not claim "only route".

### 2. "The main frame's HTTP status is available through `WKNavigationDelegate.webView(_:decidePolicyFor navigationResponse:)` by casting `navigationResponse.response` to `HTTPURLResponse`"

**Claim as written:** the cast works; `isForMainFrame` is reliable.

**Evidence.** EXTERNAL-PRIMARY throughout — `WKNavigationResponse.h` and `WKNavigationDelegate.h`, macOS 27.0 SDK, read 2026-09-09.

`WKNavigationResponse` is a four-property class: `@property (nonatomic, readonly, getter=isForMainFrame) BOOL forMainFrame;` — *"A Boolean value indicating whether the frame being navigated is the main frame"*; `@property (nonatomic, readonly, copy) NSURLResponse *response;` — *"The frame's response"*; `canShowMIMEType`; and, new, `@property (nonatomic, readonly, nullable) WKNavigation *mainFrameNavigation API_AVAILABLE(macos(27.0), ios(27.0), visionos(27.0));` — *"The most recent main frame navigation that took place that encompasses this navigation response."* The delegate method carries no availability macro, i.e. it is original macOS 10.10 API. So the cast is sound whenever the load was HTTP.

Four qualifications the statement omits:

- **Redirects: you get the final response only, and no status code for the hops.** `webView:didReceiveServerRedirectForProvisionalNavigation:` is documented as *"Invoked when a server redirect is received for the main frame"* and its only argument is a `WKNavigation`. Public `WKNavigation` has exactly one property, `effectiveContentMode`. Even the SPI is barren: `WKNavigationPrivate.h` (read 2026-09-09) has only `_request`, `_initiatingFrame` (`macos(26.0)`), `_userInitiated`. **There is no public or private way to read a 301/302/307 status or the redirect chain from `WKNavigation`.** If the product needs redirect status codes, `decidePolicyForNavigationResponse:` will not give them.
- **The response may not be an `HTTPURLResponse` at all.** `data:`, `file:`, `about:`, and any custom scheme served by your own `WKURLSchemeHandler` produce a plain `NSURLResponse` (or whatever your handler supplied). Force-unwrap and you crash. This follows directly from the property's declared type.
- **Cached and restored navigations: unreliable, and the reason is an implementation detail, not a documented contract.** Apple documents *nothing* about when this callback is skipped; the header's only discussion is *"If you do not implement this method, the web view will allow the response, if the web view can show it."* In practice WebKit drives it from the main-resource response, so a memory-cache hit still produces a synthesized response and fires it, whereas a back/forward-cache resume and a same-document navigation (`pushState`, fragment change) bypass the resource-load path and produce no `navigationResponse` at all. macOS 26 makes the first case explicit and newly *observable*: `webView:shouldGoToBackForwardListItem:willUseInstantBack:completionHandler:` (`API_AVAILABLE(macos(26.0))`) says *"If the `willUseInstantBack` argument is `YES`, then the navigation is to a webpage that is suspended in memory and might be resumed without the normal webpage loading process… In the case where the normal webpage loading process takes place, additional navigation delegate calls will continue to happen for this navigation starting with `decidePolicyForNavigationAction`."* Read that inversely: when Instant Back *is* used, they do not. Same-document navigations are only surfaced through SPI — `_webView:navigation:didSameDocumentNavigation:` in `WKNavigationDelegatePrivate.h`. **An automation driver must not treat "no navigationResponse" as "no navigation".**
- **`isForMainFrame` is reliable for what it says, and is the wrong question.** It is genuine main-frame-vs-subframe, and the callback fires for subframe navigations too, so any status-code collector that does not gate on it will attribute an iframe's 404 to the page. Until macOS 27 there was no way to tie a subframe response back to its parent navigation; `mainFrameNavigation` (macOS 27.0) is exactly that correlation key.

**Verdict: PARTLY**

**Correction to publish.** Keep the claim, add: *"the response is typed `NSURLResponse`, so the cast must be conditional — non-HTTP schemes and custom scheme handlers yield no `HTTPURLResponse`; only the final status is visible, never a redirect hop's status code, because `WKNavigation` exposes no redirect chain in API or SPI; the callback does not fire for back/forward-cache resumes (`willUseInstantBack`, macOS 26) or same-document navigations, and that omission is WebKit implementation behaviour, not a documented guarantee; and `isForMainFrame` must be checked, since subframe navigations use the same callback."*

### 3. "`WKPreferences.isFraudulentWebsiteWarningEnabled` performs a reputation check that sends hashed prefixes rather than full URLs, and it is enabled by default"

**Claim as written:** hashed prefixes are sent, not full URLs; default enabled.

**Evidence.**

- **Default: correct.** EXTERNAL-PRIMARY. `WKPreferences.h`, macOS 27.0 SDK, read 2026-09-09: *"A Boolean value indicating whether warnings should be shown for suspected fraudulent content such as phishing or malware. @discussion The default value is YES."* — `API_AVAILABLE(macos(10.15), ios(13.0))`. Apple's docs agree: <https://developer.apple.com/documentation/webkit/wkpreferences/isfraudulentwebsitewarningenabled> (read 2026-09-09) — *"The default value of this property is `true`."* Unchanged across macOS 15, 26, and 27. `WKPreferences.mm` maps it to `setSafeBrowsingEnabled`.
- **Who receives what: the statement is incomplete and slightly wrong.** EXTERNAL-PRIMARY. Apple Legal, "Safari & Privacy", document dated 2025-12-12, <https://www.apple.com/legal/privacy/data/en/safari/> (read 2026-09-09): *"Before visiting a website, Safari may send information calculated from the website address to **Google Safe Browsing and Apple** to check whether the website is fraudulent or malware has been detected. For users with **China mainland or Hong Kong** set as their region in Settings > General > Language and Region, Safari may also use **Tencent Safe Browsing** to do this check. **The actual website address is never shared with the safe browsing provider.** Google (and, for users with China mainland or Hong Kong set as their region, Tencent) **may also log your IP address** when information is sent to them."* WebKit's provider constants match: `SSBProviderGoogle`, `SSBProviderTencent`, `SSBProviderApple` in `Source/WebKit/Platform/spi/Cocoa/SafeBrowsingSPI.h` (read 2026-09-09). So: three possible providers including Apple itself, and the Tencent scope is China mainland **or Hong Kong** region — not "mainland China only".
- **"Hashed prefixes": consistent with Apple's wording, but Apple never says it, and WebKit cannot confirm it.** EXTERNAL-PRIMARY for the boundary, UNAVAILABLE for the mechanism. Apple's strongest published statements are *"information calculated from the website address"* and *"the actual website address is never shared"*. Neither the word "hash" nor "prefix" appears. WebKit hands over the **entire URL** and does no hashing at all: `Source/WebKit/UIProcess/Cocoa/SafeBrowsingUtilities.mm` (read 2026-09-09) soft-links the private `SafariSafeBrowsing` framework and calls `[context lookUpURL:url.createNSURL().get() isMainFrame:isMainFrame hasHighConfidenceOfSafety:NO cachedResult:cachedResult completionHandler:…]`. Hashing, truncation, protocol version, caching, and any proxying all happen inside closed-source `SafariSafeBrowsing.framework`. **The product may say "Apple states the actual website address is never shared with the provider"; it may not assert a hashed-prefix protocol as fact.**
- **Apple's proxying: not an Apple statement.** COMMUNITY-SIGNAL only. Apple's *current* legal text still says Google may log your IP. The widely repeated claim that Safari proxies these lookups through Apple from iOS 14.5 / macOS 11.3 traces to a tweet by Maciej Stachowiak (WebKit engineering lead) — *"In the new iOS beta, Safari does indeed proxy the service via Apple servers to limit the risk of information leak"* — as reported at <https://www.macrumors.com/2021/02/11/ios-14-5-beta-safe-browsing-safari-apple-google/> and <https://9to5mac.com/2021/02/11/fraudulent-website-warning/> (both read 2026-09-09). Apple has published no such statement in legal, support, developer, or Platform Security material. Do not present proxying as Apple's position.
- **Scope: navigations, not "every page".** EXTERNAL-PRIMARY. `SafeBrowsingUtilities.h` defines `enum class NavigationType : bool { MainFrame, SubFrame };` and `WebPageProxy::beginSafeBrowsingCheck` (`Source/WebKit/UIProcess/Cocoa/WebPageProxyCocoa.mm`, read 2026-09-09) runs the lookup for main-frame **and** subframe navigations, once **per URL in the redirect chain** (`navigation.redirectChainIndex(url)`). It does **not** run on ordinary subresource loads. Gated by `HAVE(SAFE_BROWSING)` — `PLATFORM(MAC) || IOS || WATCHOS || MACCATALYST || VISION` (`Source/WTF/wtf/PlatformHave.h`), so tvOS is excluded and non-Apple ports are inert.
- **Third-party WKWebView vs Safari.** EXTERNAL-PRIMARY for the code path: identical, no Safari-only branch in the open-source path. Differences that matter: the default is on in every WKWebView and the embedder can silence it in one line with no user-visible way to re-enable, whereas Safari exposes a user toggle; and WebKit draws the interstitial itself (`BrowsingWarningCocoa.mm`), notifying the app only through SPI `_webViewDidShowSafeBrowsingWarning:` (`macos(10.14.4)`). Whether the closed framework treats Safari differently (entitlements, list freshness, proxy use) is UNAVAILABLE.

**Verdict: PARTLY**

**Correction to publish.** Keep "enabled by default" (documented, `true`, since macOS 10.15). Replace the mechanism sentence with: *"When enabled, WebKit passes each main-frame and subframe navigation URL — including every URL in a redirect chain — to the system's private `SafariSafeBrowsing` framework, which performs the lookup. Apple states that 'information calculated from the website address' is sent to Google Safe Browsing and to Apple, that 'the actual website address is never shared with the safe browsing provider', and that Google may log your IP address; for users whose region is China mainland or Hong Kong, Tencent Safe Browsing may also be used. Apple does not publish the wire protocol, so we do not assert a hashed-prefix scheme, and Apple has published no statement that it proxies these lookups. The check does not run on ordinary subresource loads."*

### 4. "There is no official WKWebView API to observe the page's `console` output; an embedder must inject a script that forwards it"

**Evidence.** EXTERNAL-PRIMARY.

Grepping every public header in the macOS 27.0 SDK's `WebKit.framework/Headers` for `console` (read 2026-09-09) returns nothing in the `WK*` modern API — the only hits are in deprecated WebKitLegacy headers and in unrelated prose. The Swift-side surface is equally empty: grepping `WebKit.swiftmodule/arm64e-apple-macos.swiftinterface` for `console`, `consoleMessage`, or `logMessage` returns zero matches, so the new SwiftUI `WebPage` (macOS 26) added nothing either. Nothing at WWDC 2025 or WWDC 2026 changed it: neither <https://webkit.org/blog/17333/webkit-features-in-safari-26-0/> nor <https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/> (both read 2026-09-09) lists a console API for embedders, and the macOS 27.0 SDK availability diff for `macos(26` / `macos(27` contains no such symbol.

One change is worth recording because it will tempt someone: `Source/WebKit/UIProcess/API/Cocoa/WKUIDelegatePrivate.h` (read 2026-09-09) now declares

```objc
- (void)_webView:(WKWebView *)webView didReceiveConsoleLogForTesting:(NSString *)log
  WK_API_AVAILABLE(macos(26.4), ios(26.4), visionos(26.4));
```

This is **SPI, and named `ForTesting`** — Apple is signalling both that it is private and that it is not a supported product surface. It delivers a flat string, not a structured message with level, source URL, or line number. Do not build on it and do not cite it as an API.

So the injection route remains the only shippable one. It has the same integrity ceiling as statement 1's `fetch` patch: script injected into `WKContentWorld.pageWorld` is patchable by the page. macOS 27 helps here — `WKContentWorldConfiguration` (macOS 27.0) lets an isolated world be created with `allowAccessingClosedShadowRoots`, `elementUserInfoEnabled`, and `isInspectable` control, and forwarding from a non-page content world via `WKScriptMessageHandler` keeps the *transport* out of the page's reach. But `console.log` itself lives in the page world, so the *hook* is still page-visible whatever world the receiver lives in. That distinction is worth stating precisely rather than blurring.

**Verdict: CONFIRMED**

Refinement, not correction: add that a `_webView:didReceiveConsoleLogForTesting:` SPI appeared in macOS 26.4 and is explicitly test-only, and that injecting into an isolated content world hardens the forwarding path but not the hook.

## New for embedders in macOS 26 and 27

Only items with a concrete use for driving and observing a page under automation. All EXTERNAL-PRIMARY from the macOS 27.0 SDK read 2026-09-09, cross-checked against <https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/> and <https://webkit.org/blog/17333/webkit-features-in-safari-26-0/>.

### macOS 27 — adopt these

1. **`WKJSHandle` + `WKContentWorldConfiguration.jsHandleCreationEnabled` + `WKWebpagePreferences.allowsJSHandleCreationInPageWorld`.** A durable, GC-protected reference to a live JavaScript object, obtained when page script calls `window.webkit.createJSHandle(…)`, carrying `sourceFrame`, `contentWorld`, and `getWindowProxyFrame`, and usable as an argument to a later `callAsyncJavaScript:`. **This is the native element-handle primitive** — the thing every Chromium-based automation stack has and WKWebView did not. It replaces the usual `data-automation-id` round-tripping: resolve a locator once, hold the handle, act on it later, with WebKit telling you (via `undefined`) when the frame navigated out from under you. Highest-value item in either release for this product.
2. **`WKDOMNodeSnapshot` + `WKContentWorldConfiguration.nodeSnapshotCreationEnabled`.** The complement to `WKJSHandle`: an opaque node reference created by `window.webkit.createNodeSnapshot(…)` that, unlike a handle, is *not* tied to a live JS object and so survives being passed into a different frame or used after a navigation. The right carrier for a locator you want to persist across a page transition. (Announced as `WKSerializedNode`; shipped as `WKDOMNodeSnapshot` — check the SDK, not the blog post.)
3. **`WKContentWorldConfiguration.allowAccessingClosedShadowRoots`** (`WKContentWorld.init(configuration:)`). Closed shadow roots become traversable from your isolated world without touching the page world. Removes a whole class of "element not found" failures on component-framework sites, and does it without a page-visible patch.
4. **`WKNavigationDelegate.webView:willSubmitForm:submissionHandler:` + `WKFormInfo`** — `targetFrame`, `sourceFrame`, `submissionURL`, `httpMethod`, and `formValues` (the actual dictionary of values about to be submitted), with an async submission handler you must invoke. Public API for the transactional-form-write pre-condition check this repo previously had to approximate. Also on the SwiftUI side as `WebPage.NavigationDeciding.willSubmit(formInfo:)`.
5. **`WKWebpagePreferences.alternateRequest`** — *"Used to make changes to the network request that will be used for this navigation's main resource load"*, set from `decidePolicyForNavigationAction:preferences:`. Per-navigation header and request rewriting without rebuilding the load. Pairs with **`overrideReferrer`** (a `referer` applied to *all* resource loads in the frame) and **`globalPrivacyControlEnabled`** (`navigator.globalPrivacyControl` + `Sec-GPC: 1`, default `NO`).
6. **`mainFrameNavigation` on both `WKNavigationAction` and `WKNavigationResponse`.** The correlation key that lets a driver attribute a subframe action or response to the main-frame navigation that encompasses it. Directly fixes the statement-2 attribution hazard.
7. **`WKUserContentController.addBuffer(_:name:to:)` / `removeBuffer(named:from:)`** (Swift: `RawSpan`). Hand binary data to a content world without base64-ing it through a JS string. Relevant to file-upload payloads and large fixtures.
8. **`WKWebView.load(_:)` taking a bare `URL`.** Cosmetic, but it removes a `URLRequest` wrapper from every navigation call site.

### macOS 26 — adopt these

9. **`WKWebView.fetchData(of:)` / `restoreData(_:)` and `WKWebsiteDataStore.fetchData(of:)` / `restoreData(_:)`.** Serialize and restore web-view state as an opaque `Data` blob; `WKWebViewDataType` currently offers `sessionStorage`. The public answer to session persistence and warm-start across process launches — previously only reachable by scraping cookies and re-running scripts.
10. **`WKHTTPCookieStore.getCookies(for:)` and batch `setCookies(_:)`.** Per-URL cookie read instead of enumerating the whole store, and one batched write instead of N serialized calls. Straight throughput win on session setup and teardown.
11. **`WKNavigationDelegate.webView:shouldGoToBackForwardListItem:willUseInstantBack:completionHandler:`.** Tells you, before the fact, that a back/forward navigation will resume a suspended page and therefore will *not* replay the normal delegate sequence. An automation driver that waits on `didFinish` after `goBack()` needs this to avoid hanging or mis-sequencing.
12. **`WKWebView.isBlockedByScreenTime` + `WKWebViewConfiguration.showsSystemScreenTimeBlockingView` + `WKWebsiteDataTypeScreenTime`.** Lets the driver distinguish "the site is blocked by policy" from "the navigation failed", instead of reporting a bogus network error.
13. **`WKNavigationAction.isContentRuleListRedirect`.** When you use a content rule list to redirect (a legitimate automation technique for stubbing), you can now tell your own redirect apart from the site's.
14. **`WKWebView.obscuredContentInsets`** (macOS 26). Shrinks the layout viewport for client-managed chrome. Anything doing coordinate-based actuation or viewport-relative screenshots needs this correct or every click lands offset.
15. **SwiftUI `WebView` + `WebPage` (macOS 26).** `WebPage` is `@Observable` with `url`, `title`, `isLoading`, `estimatedProgress`, `serverTrust`, `backForwardList`; every `load(…)` returns `some AsyncSequence<WebPage.NavigationEvent, any Error>` (`startedProvisionalNavigation`, `receivedServerRedirect`, `committed`, `finished`) with a typed `NavigationError` (`failedProvisionalNavigation`, `pageClosed`, `webContentProcessTerminated`, `invalidURL`); plus `callJavaScript`, `callAsyncJavaScript`, `pdf(configuration:)`, `NavigationDeciding`, `DialogPresenting`, and a Swift `URLSchemeHandler` protocol over `AsyncSequence`. For an automation driver this is the important structural change: **navigation becomes an awaitable sequence with a typed terminal error instead of delegate bookkeeping plus a continuation and a timeout.** Session: <https://developer.apple.com/videos/play/wwdc2025/231/> ("Meet WebKit for SwiftUI", read 2026-09-09). Cost: macOS 26 floor, so it cannot replace the `WKWebView` path while macOS 15 is supported — run it as a parallel driver behind an availability check.
16. **`WKWebpagePreferences.securityRestrictionMode`** (macOS 26.4). Per-navigation isolated WebContent processes at a chosen protection level; main-frame only, inherited by subframes and opened windows, default `WKSecurityRestrictionModeNone`, and silently ignored when the system has already chosen Lockdown. Relevant to running untrusted targets in a hardened process.

### Explicitly not worth adopting

- `NSRefreshController` on `WKWebView` (macOS 27, macOS-only): pull-to-refresh chrome. No automation value.
- `_webView:didReceiveConsoleLogForTesting:` (macOS 26.4): SPI, test-only, unstructured. See statement 4.
- Safari 27's Web Inspector improvements (redirect chains in the Network tab, colour-contrast in the picker, Grid-Lanes badges): human-facing, no embedder surface.

## Unavailable

- **The Safe Browsing wire protocol.** Hash length, prefix scheme, protocol version, request batching, caching policy, and whether Apple proxies the lookup are all inside the closed `SafariSafeBrowsing.framework`, soft-linked by WebKit. Not in Apple docs, not in WebKit source. Apple's only published characterisation is "information calculated from the website address" plus "the actual website address is never shared with the safe browsing provider".
- **Apple's own statement that it proxies Safe Browsing lookups.** None exists in developer, legal, support, or Platform Security material. Apple's current legal text (2025-12-12) says the opposite about IP logging. Only COMMUNITY-SIGNAL (press reporting of a WebKit engineer's tweet, 2021).
- **Whether `SafariSafeBrowsing` treats Safari differently from a third-party WKWebView host** (entitlements, list freshness, telemetry, proxy use). Not observable in open source, not documented.
- **Documented behaviour of `decidePolicyForNavigationResponse:` on back/forward-cache restores and same-document navigations.** Apple documents only the default-allow behaviour. The skip is inferred from WebKit's load path and corroborated by the `willUseInstantBack` header comment. Treat as implementation detail, not contract.
- **`UnifiedWebPreferences.yaml` default line for `SafeBrowsingEnabled`.** File too large to fetch in full; the header and Apple docs both state the default, so this is a redundancy gap only. (`WebPreferences.yaml` no longer exists; there is no `WKPreferencesGetSafeBrowsingEnabled` in the C API.)
- **WWDC 2026 session material on native embedder API.** <https://developer.apple.com/videos/play/wwdc2026/204/> ("What's new in WebKit for Safari 27", read 2026-09-09) is web-platform-only. The macOS 27 embedder additions are documented in the SDK headers and the WebKit blog post, not in a session.
- **Whether a sandboxed App Store macOS app can install a system-trusted root CA without user admin authentication**, and which network entitlements a bundled local proxy listener needs. Both are hard gates on the `proxyConfigurations` route and neither was verified here. Almost certainly the CA answer is no, which would make that route usable only for a Developer ID / internal build, or with a user-driven trust step.
- **Whether `WKWebExtension`'s `webRequest` really is macOS-only.** Apple's permission constant says `ios(18.4)`; Apple's Safari extension compatibility table says *"Not supported in iOS"*. Unresolved contradiction between two Apple sources — test before relying on it off macOS.
- **Whether the resource-load events actually flow for a host app's `WKWebView`s once registered as `WKWebExtensionTab`s.** The WebKit-internal plumbing (`WebExtensionController::resourceLoadDid*`, `hasPermissionToSendWebRequestEvent`) makes this near-certain, but it is inference from source signatures, not a documented guarantee or a measured result. Prototype it before publishing a capability claim built on it.
