# Tool-surface gap matrix: WebKitUI MCP against every competitor

Date: 2026-09-09

Question: Tool by tool, what can a competing browser MCP server or agentic browser do that this product cannot, and for each absence, is it a refusal, a WKWebView ceiling, a real gap, or a web-development convenience that does not matter?

Method. This product's surface was read from source, never from `README.md`; every claim about it carries a file and line. Competitor surfaces were read from the vendor's own tool definitions where obtainable: Playwright MCP's and Chrome DevTools MCP's published tool references, Apple's 17 tools as recorded in `docs/research/2026-09-09-apple-safari-mcp-server.md` (blog table plus a local `tools/list` handshake), and Claude in Chrome's live MCP schemas as exposed to this Claude Code session and read today. WKWebView reachability was judged against the macOS 27.0 SDK shipped in Xcode-beta on this machine (`.../MacOSX27.0.sdk/System/Library/Frameworks/WebKit.framework/Headers`, read 2026-09-09) and `docs/research/2026-09-09-wkwebview-capability-ceiling.md`. No capability is inferred from marketing language.

---

## Verdict

For the job this product actually claims — one approved, provenance-carrying, receipt-bearing write at a time on a site the user is genuinely logged into — the surface is close to complete, and its refusals (no JavaScript, no CDP, no tabs, no cookie access) are coherent rather than lazy. Where it falls short is not autonomy but *reach*: a large class of ordinary controls on ordinary authenticated sites cannot be operated at all, and the failures are silent rather than diagnosable. The single most costly absence is not any of the four already known — it is that **cross-origin iframe content is invisible and unaddressable** (`Sources/WebKitUIMCPRuntime/WebKitRuntime.swift:4029-4033` counts such frames and stops), which removes every hosted payment field, every CAPTCHA, and every embedded SSO or support widget from the agent's world; a checkout is exactly the task the product is built for and exactly the task this makes impossible. Ranked immediately behind it, and jointly larger than the four known gaps, are the keyboard restricted to Enter/Tab/Escape (`WebKitRuntime.swift:2715-2723`), which forecloses the ARIA combobox that has replaced `<select>` on modern checkouts, and `target="_blank"` navigation being silently cancelled with no `createWebViewWithConfiguration:` implemented (`WebKitRuntime.swift:2095-2097`), which kills invoice, statement and report links. The four known gaps are all real, all correctly diagnosed as to symptom, but two are misclassified as to cause: JavaScript dialogs are trivially implementable public API, while a *trusted* `<select>` choice is probably not reachable at all — the honest fix there is an untrusted one, which is a policy decision the product has not yet made.

`browser_act` operations (`MCPServer.swift:3899-3906`), and what each really reaches:

- `click` — native `NSEvent` `.leftMouseDown` + `.leftMouseUp` at the target's centre under `approval_mode: "native"` (`WebKitRuntime.swift:2562-2584`); JavaScript dispatch under `mcp`.
- `submit` — a native form-submit *control* click; it is not a separate runtime operation. The runtime enum has five members, not six: `WebKitActionOperation` = `click`, `fill`, `pressKey`, `blur`, `commitInput` (`WebKitRuntime.swift:310-316`).
- `fill` — `value` up to 4096 chars (`MCPServer.swift:3908-3911`). Gated to `HTMLInputElement`, `HTMLTextAreaElement` or `isContentEditable`, and not `readOnly` (`WebKitRuntime.swift:4799-4802`). Empty string clears. Postcondition is *forbidden* for `fill`; its exact value and live validation state are verified automatically.
- `press_key` — schema enum `Enter`, `Tab`, `Escape` only (`MCPServer.swift:3915-3917`), and the native dispatcher hard-codes exactly those three keycodes (36, 48, 53) and throws `targetNotActionable` on anything else (`WebKitRuntime.swift:2715-2723`). No modifiers are ever set.
- `blur`, `commit_input` — JavaScript-dispatched, reported untrusted.

Postconditions (`MCPServer.swift:3722-3820`) are richer than any competitor's assertion surface: `url_equals`/`url_contains`/`url_changes_from`, `title_*`, `heading_*`, `semantic_text_appears`/`_contains`, `checked_equals`, `selected_equals`, `enabled_equals`, `value_equals`, `option_selected` (3786), `dialog_appears` (3785), and `attribute_equals` over an allowlist of seven ARIA/state attributes. Two things to note: `dialog_appears` resolves to an **in-page** modal (`document.querySelectorAll('dialog[open], [role="dialog"]…')`, `WebKitRuntime.swift:4609`), not a JavaScript dialog; and `option_selected` is the read-only twin of the missing select operation.

Viewport is fixed at 1280×800 in two places (`WebKitRuntime.swift:522`, `WebKitRuntime.swift:1680`). `WKUIDelegate` conformance is declared (`WebKitRuntime.swift:410`) but only one delegate method is implemented: `runOpenPanelWith` (`WebKitRuntime.swift:1347-1349`). Same-origin iframes and shadow roots *are* traversed (`WebKitRuntime.swift:3305-3323`); cross-origin frames are counted and abandoned (`WebKitRuntime.swift:4029-4033`). Cookies are touched only internally, for a profile check and a wipe (`WebKitRuntime.swift:1316`, `1770-1775`); no tool exposes them. `localhost`, `*.local` and IP literals are refused before DNS (`Sources/WebKitUIMCPRuntime/PublicNetworkAddressPolicy.swift:26-29`).

- **Claude in Chrome** is the only one whose surface can be read directly, because its tools are exposed to Claude Code (`mcp__claude-in-chrome__*`, schemas read 2026-09-09). The honest summary of the consumer tier: none of them lacks any capability this product lacks. They are all full browsers driven at the pixel or DOM level. The comparison that favours this product is not capability, it is who owns the approval and whether a receipt exists afterwards — not reach.

## Real gaps, ranked

Ranked by how often the gap stops a real task on a real authenticated site.

**1. Cross-origin iframe content is invisible.** `deepQueryAll` descends into same-origin frames and shadow roots but a cross-origin frame is only tallied into `crossOriginFrameCount` (`WebKitRuntime.swift:4029-4033`), so nothing inside it can be observed, inspected or acted on. *Blocks:* every checkout whose card number, expiry and CVC are hosted fields — Stripe Elements, Adyen, Braintree, Checkout.com, most PSP integrations; reCAPTCHA and hCaptcha; embedded SSO and OIDC login frames; Zendesk/Intercom support widgets; embedded Google Docs, Maps and calendar pickers. The failure presents as "the field is not on the page", which is the worst possible diagnostic. *Implementing it needs:* a frame inventory and per-frame instrumentation. `WKFrameInfo` is only ever handed to an embedder inside delegate callbacks, and `callAsyncJavaScript(…, in:)` accepts one, so the plausible design is to accumulate `WKFrameInfo` from `decidePolicyFor navigationAction/Response` (the runtime already inspects `targetFrame` at `WebKitRuntime.swift:2055`, `2095`, `2868`) and run the observation script in each. Whether a *complete* frame inventory is reachable this way is UNAVAILABLE — untested. *Approval complication:* substantial and interesting. An element inside a third-party frame has a different origin from the page the human approved; the confirmation text would have to name that origin, and the origin lock (`topLevelOriginLock`) and the authentication-origin fail-closed rules would both need a frame-aware definition. This is the largest single piece of work in this document and also the highest-value.

**2. The keyboard is three keys.** Schema enum and native dispatcher both admit only Enter, Tab, Escape, with no modifier flags (`MCPServer.swift:3915-3917`, `WebKitRuntime.swift:2715-2723`). *Blocks:* the ARIA combobox, which is what replaced `<select>` on modern checkouts and admin consoles — react-select, Downshift, Headless UI, Algolia autocomplete, Google/Stripe address autocomplete, and most country and currency pickers on new payment pages. These render as a text input plus a listbox; you type, then you must press ArrowDown and Enter, and ArrowDown does not exist. Also blocks: date pickers driven by arrow keys, Space to toggle a focused checkbox or open a listbox, Backspace to clear a token field, `cmd+A` before retyping, and Shift+Tab to go back one field after overshooting. *Implementing it needs:* extending the keycode map in `dispatchNativeKey` and widening the schema enum; the `NSEvent.keyEvent` machinery, the armed-gesture token, and the `isTrusted` receipt already exist and are unchanged. This is the cheapest item on the list relative to what it unlocks. *Approval complication:* mild but real — a key with a modifier is a different act from a key without one, and the dialog must state the full chord; an unbounded key surface also starts to approximate typing, which `fill` already handles under its own provenance rules, so the enum should stay an allowlist (arrows, Space, Backspace, Delete, Home/End, PageUp/PageDown, Shift+Tab) rather than becoming free-form.

**3. `target="_blank"` and `window.open()` do nothing, silently.** `createWebViewWithConfiguration:` is not implemented anywhere in `Sources/`, and under an origin lock a `nil` target frame is cancelled outright (`WebKitRuntime.swift:2095-2097`). *Blocks:* "View invoice", "Download statement", "Open report", "Print packing slip" and "Terms" links on virtually every billing portal, bank, SaaS admin and airline site — all conventionally `target="_blank"`; OAuth and 3-D Secure popups; "open in new tab" affordances in consoles. The click is approved, dispatched, reported as trusted, and nothing happens, so the postcondition fails and the agent has no way to tell an unresponsive control from a suppressed window. *Implementing it needs:* implement `createWebViewWithConfiguration:` (public, `WKUIDelegate.h:97`), return `nil`, and load `navigationAction.request` into the existing web view — which is the standard embedder pattern and preserves "one session, one page". *Approval complication:* it becomes a navigation, so it should route through the same native destination confirmation `browser_navigate` uses, and the cross-origin case should reuse `redirect_requires_human_approval`. Alternatively, refuse it but say so: returning a distinct `new_window_suppressed` outcome instead of silence would recover most of the value at a fraction of the cost.

**4. `<select>` cannot be set.** The selected option is observed and assertable (`WebKitRuntime.swift:3902-3919`; `option_selected`, `MCPServer.swift:3786`) but no operation chooses one, and `fill` is gated to input/textarea/contentEditable (`WebKitRuntime.swift:4799-4802`). *Blocks:* country and state on any checkout or shipping form, card expiry month and year where the PSP renders native selects, title/salutation, date-of-birth triples, quantity, currency, timezone, and the filter dropdowns on older admin consoles. Very common, and unlike gaps 1-3 it is usually the *only* blocker on an otherwise completable form. *Implementing it needs:* a decision the product has not yet made, and this is a correction to the brief's framing. The JavaScript route is easy — set `selectedIndex` and dispatch `change`, exactly the path `fill` already takes under `approval_mode: "mcp"` — but the resulting `change` event is `isTrusted == false`, so it must be reported untrusted, and some sites' validation ignores untrusted change events. A *trusted* native selection would mean driving the popup WebKit renders as an `NSMenu`, into which synthetic `NSEvent`s posted at the web view do not go; whether any public route exists is **UNAVAILABLE** and I would not assume one. So the shippable fix is an untrusted `select_option` operation, honestly labelled, sitting alongside the trusted operations. *Approval complication:* moderate — the dialog can name the exact option label and the exact `<select>`, which is a good confirmation; the awkwardness is purely that the product would be admitting a second-class dispatch path in a family it has otherwise kept trusted.

**5. JavaScript dialogs cannot be answered.** No `runJavaScriptAlertPanel`, `ConfirmPanel` or `TextInputPanel` on the delegate (`WebKitRuntime.swift:410`, only `runOpenPanelWith` at `1347-1349`), so WebKit takes the unimplemented default. Measured on this machine today: `confirm()` returns `false` and `prompt()` returns `null`, on every site, silently. `alert()` being dropped follows from the same absent delegate but was not separately measured. *Blocks:* any destructive control guarded by `confirm()` — "Delete", "Cancel subscription", "Remove member", "Revoke key", "Empty trash" on older admin panels, cPanel-style hosts, WordPress and phpMyAdmin-lineage tools, and a long tail of internal enterprise apps. The click succeeds, the confirm silently answers *no*, and the postcondition then correctly reports that nothing changed — which reads as "the button doesn't work". *Implementing it needs:* three public delegate methods (`WKUIDelegate.h:120`, `:136`, `:154`), each already suited to this product's model: the message text comes from the page, not the agent, so the native confirmation can quote it verbatim, which is the strongest form of the product's own differentiator. `browser_act` would need the dialog to be answerable as part of the approved action rather than as a separate tool call, since the completion handler must be invoked before the page continues. *Approval complication:* favourable, not adverse. The one genuinely blocked sibling is `beforeunload`, which has no public delegate at all (no `BeforeUnload` symbol in the macOS 27.0 SDK public headers) — so navigating away from a dirty form remains WebKit's decision, not the product's. *Rank note:* placed fifth rather than first only because `confirm()`-guarded controls are concentrated in older and internal software, whereas gaps 1-4 hit mainstream commerce and SaaS every day. On an admin-heavy workload it is first.

**6. No back, forward or reload.** Zero occurrences of `reload`, `goBack`, `goForward` or `history` in `MCPServer.swift`. *Blocks:* recovery. A misresolved click that navigates somewhere unintended is unrecoverable except by re-navigating to a URL, and `browser_observe` redacts URL query values (`MCPServer.swift:4037`) — so after landing on a deep, query-bearing page the agent may no longer possess the URL it needs to get back. Also blocks re-reading a page whose observation went stale mid-task, and escaping a transient 5xx error page without a fresh approved navigation. *Implementing it needs:* `WKWebView.goBack()`/`goForward()`/`reload()`, plus `webView:shouldGoToBackForwardListItem:willUseInstantBack:` (macOS 26) so the driver does not hang waiting for delegate callbacks that Instant Back skips — the capability-ceiling document flags exactly this hazard. *Approval complication:* real. Back is a navigation to a destination the agent cannot fully name, so the native dialog would have to describe it as "back to \<origin+path of the previous entry\>", and the origin lock must be re-evaluated on arrival rather than before departure. Reload is easier and worth shipping first: same URL, same origin, nothing new to approve beyond the fact of re-fetching.

**7. Viewport fixed at 1280×800.** `WebKitRuntime.swift:522` and `1680`. *Blocks:* less than it appears, because 1280×800 is a reasonable desktop and the observation is full-page rather than viewport-clipped. What it does block: sites whose responsive breakpoints hide or restructure controls at that exact width (some enterprise consoles collapse a sidebar under 1366 and hide actions behind a hamburger the semantic walk then reports as a single button); tall fixed-height layouts where a modal's action row is unreachable because the modal itself scrolls internally; and any full-page capture, since `WKSnapshotConfiguration.rect` must stay inside the view's bounds (`WKSnapshotConfiguration.h:37-41`). *Implementing it needs:* a resize of the hosting view plus a re-layout and observation invalidation. Nothing in WebKit resists it. Mobile *emulation* is separate and is genuinely blocked — no `ContentMode` API on macOS. *Approval complication:* none worth mentioning; it is a read-shaping operation, not a write. Pair it with a `createPDFWithConfiguration:`-based full-page capture and both minor gaps close together.

**8. Hover.** Kept on the list because it does block real tasks, but classified as blocked rather than as an oversight: WebKit does not forward `NSEventTypeMouseMoved` to the underlying view, and WebKit's own automation needed private `_simulateMouseMove:` to make hover work (`docs/research/2026-09-09-trusted-input-fidelity.md:36`, `:102`). *Blocks:* hover-revealed navigation menus in AWS and older enterprise consoles; row-action buttons that only render on `:hover` in tables (Grafana, many admin grids); tooltips that carry the only label a control has. *Implementing it needs:* a decision to dispatch an untrusted `mouseover`/`mouseenter`/`pointerover` sequence via the instrumentation world and report it as untrusted — the same bargain as gap 4. *Approval complication:* hover is not itself a write, which makes an untrusted hover much easier to justify than an untrusted click; the risk is that hover-then-click becomes a two-call idiom in which the first call's effect has expired by the time the second is approved, since any observation is invalidated in between.

**9. Media and geolocation permission requests are silently denied.** `requestMediaCapturePermissionForOrigin:` (`WKUIDelegate.h:165`) and `requestGeolocationPermissionForOrigin:` (`WKUIDelegate.h:302`) are public and unimplemented. *Blocks:* identity-verification flows that want a camera, and store-locator or delivery-address flows that want a location. Low frequency, and arguably the product should refuse both — but it should refuse them *loudly*, with a named outcome, rather than by not answering.

**10. Minor and cheap:** double/triple click; `browser_scroll` on an inner container rather than only the top-level page (`MCPServer.swift:4102`); a PDF save; a file *drop* onto a zone with no underlying `<input type=file>`.

## Deliberate refusals, restated with their reasons

None of the following is an oversight, and each should be read as a claim the product is making rather than a feature it has not got to.

- **Arbitrary JavaScript evaluation.** Every competitor except Browserbase's 6-tool MCP server exposes it, including Apple's own server. The reason is stated in `README.md:81`: "one JavaScript-evaluation call would do anything the confirmation exists to authorize one action at a time". A per-action gate and an eval tool cannot coexist; whichever is second is decoration.
- **Raw CDP.** Same reason, and mechanically unavailable in WebKit besides. Chrome DevTools MCP and Browser Use sit on CDP as substrate; neither exposes it as a tool, so the honest comparison is about substrate power, not tool surface.
- **Multiple tabs and new-window handling.** `README.md:82`: "One session holds one exclusive host lease, which is what lets an approval refer to an unambiguous page." Note the separation argued in ranked gap 3: refusing *tabs* is coherent; silently cancelling a `target="_blank"` navigation is not the same decision and is the part worth revisiting.
- **Coordinate-based actuation.** `README.md:81` lists "coordinate retry" among the refusals. A coordinate cannot be re-resolved, cannot be named in a confirmation dialog, and cannot carry locator quality — it is incompatible with the addressing model, not merely riskier than it.
- **Batched action sequences.** Apple's `page_interactions` runs a list "sequentially with a 400 ms settle between each"; Claude in Chrome's `browser_batch` runs any sequence in one round trip. Both are one authorization for N dispatches. That is the precise property this product exists to deny, and a batch tool would silently undo every other control.
- **Cookie, localStorage and sessionStorage access.** Playwright MCP exposes seventeen storage tools including `browser_storage_state`, which writes a portable session credential to a file. This product's authentication claim is that MCP receives no credential and no session token; the SiliconPass tools exist precisely so that a value can be filled without crossing the boundary. A cookie read would hand over both and make the credential design pointless.
- **Network request mocking and routing.** A server that can forge a site's responses cannot also claim its `ReceiptV1` is evidence of what the site actually did. Observation of network traffic is a different question and is a real gap (see below).
- **Page-authored tools (WebMCP, third-party developer tools).** Chrome DevTools MCP will enumerate and execute tools the page itself advertises. A tool list written by the page is the page giving the agent instructions, which is the injection channel every other control in this product is built to close.
- **`localhost`, `*.local` and IP literals.** `PublicNetworkAddressPolicy.swift:26-29` refuses them before DNS. Worth stating plainly in any comparison: it means this product cannot do the job Apple's server is *for*. That is a positioning choice, not a shortfall — but a reader comparing tool counts will otherwise mistake it for one.

## Architecturally interesting, not merely missing

**Apple's UID addressing versus observation-scoped element IDs.** Apple's `get_page_content` returns node UIDs that `page_interactions` and `evaluate_javascript` then reference, with a `$uid(N)` macro inside JavaScript and no separate snapshot or element-inspection tool. This product's IDs are deliberately *worse* in a way that is the point: they are scoped to one observation and invalidated by scrolling or acting (`browser_observe` 4037, `browser_scroll` 4102, `element_scroll_into_view` 4113), and the runtime re-resolves the target and verifies geometry stability against the expected box before dispatch, in each of the four action paths (`WebKitRuntime.swift:4778`, `4878`, `4917`, `4952`). Apple's UID is a convenience that lets an agent hold a reference across a page change; this product's ID is a lease that expires so an approval can never be spent on a different element than the one described. Judgement: the right trade for this product, and the cost is round trips. The genuinely better option is now public — `WKJSHandle` and `WKDOMNodeSnapshot` (macOS 27), which the capability-ceiling document calls "the native element-handle primitive… Highest-value item in either release for this product". A durable handle that WebKit itself invalidates on navigation would give freshness *and* stability, which is strictly better than either scheme.

**Apple's `get_page_content` markdown output.** Options are `region` (viewport / entire_page), `format` (markdown, text, textTree, json, html, plainText), `includeAccessibilityAttributes`, `includeSubframes`, `maxWordsPerParagraph`, `nodeIds` (none / editable / interactive / allContainers), with output over 32 kB spilled to a temp file. Its own description says it is "the preferred way to read a page — favor it over screenshots or scripting the DOM". Two things worth taking. First, `nodeIds: interactive|editable` is a cleaner articulation of the same idea as this product's `roles` filter, and `maxWordsPerParagraph` is a summarisation knob this product has no equivalent of (`maximum_field_characters` bounds fields, not prose). Second, markdown as the wire format is a real advantage for reading dense documents — a statement, an invoice, a policy page — where this product's `browser_read_text` returns flat text plus region records (4080) and loses table and heading structure. Judgement: worth adopting a structured reading format; *not* worth adopting the spill-to-temp-file behaviour, which puts page content on disk outside the receipt discipline.

**Claude in Chrome's `browser_batch`, judged rather than copied.** Its description is unusually candid about the cost: "Each tool's own permission check runs per item — if an action navigates to a domain without permission, the next item's check fails and the batch stops", and "coordinates you write in THIS batch refer to the screenshot taken BEFORE this call". That second sentence is the whole argument against batching for this product: a batch is a plan written against a stale world. Worth recording that the batching model does not weaken *its* permission checks, only its addressing.

**Playwright MCP's `element` parameter as the anti-pattern.** An optional string, "Human-readable element description used to obtain permission to interact with the element" — the agent writes the text the human reads, and may omit it. This is the sharpest available contrast with a server-computed dialog and it is already recorded in the approval-landscape document; it belongs here too because it is an *architecture*, not a missing tool: permission text as a model output rather than a server measurement.

**Playwright's capability flags (`--caps=vision,pdf,devtools,network,storage,testing`) gate surface, not authority.** Worth naming because it looks like a security control and is not; this product's equivalent — `authenticationRestrictedTools` (`MCPServer.swift:3708-3722`) and the `CapabilityScope` of seven actions bound to origins, provenance classes and an expiry (`Sources/WebKitUIMCPCore/CapabilityAuthority.swift:3-11, 21-26`) — gates authority per call. The distinction is the more publishable claim than any tool count.

**The network-observation gap is a near-miss, not a ceiling, and the product is already halfway there.** The capability-ceiling document explicitly refutes "no API": `WKWebsiteDataStore.proxyConfigurations` is public since macOS 14 and is Apple DTS's own recommended answer, and a bundled `WKWebExtension` with the `webRequest` permission is public since macOS 15.4 and yields URL, method, resource type, frame identity, redirect target, status and timing for `xmlhttprequest` and `websocket` loads from outside the page's reach. This repository already ships `Sources/WebKitUIMCPRuntime/PinnedSOCKSProxy.swift`, so the transport half of the proxy route exists. Why it matters more here than for any competitor: this product's central claim is that "UI state does not prove backend commit" (`browser_act`, 3894) and its `browser_transaction reconcile` operation currently reconciles an indeterminate write against a *fresh observation* — that is, against more UI. A response status for the request the approved click actually caused would turn reconciliation from inference into evidence. That is the one place where a capability this product lacks is directly load-bearing for a claim it already makes, and it is the item I would put ahead of everything in the ranked list if the goal were the strongest product rather than the most tasks completed.

**Postconditions as an architecture the field does not have.** Playwright's `browser_verify_*` family and Chrome's `wait_for` are separate calls after the fact; this product's postcondition is an argument to the action, schema-required for click, submit, press_key, blur and commit_input and schema-forbidden for fill (`MCPServer.swift:3722-3820`, and the `allOf` conditionals at `3930-3971`), and evaluated against a re-resolved target. Nobody else binds the assertion to the authorization. Recording it here because a reader scanning the matrix will count tools and miss it — and because `dialog_appears` (3785) and `option_selected` (3786) show the postcondition surface already anticipating two of the ranked gaps, which is a decent argument that the gaps were noticed before they were closed.

## Unavailable

- **Whether a complete cross-origin frame inventory is reachable from public WKWebView API.** `WKFrameInfo` is only handed to an embedder inside delegate callbacks and `callAsyncJavaScript(…, in:)` accepts one, but no public frame-enumeration property was located in the macOS 27.0 SDK headers. Untested. Ranked gap 1 assumes accumulation from navigation callbacks is sufficient; that assumption is not verified.
- **Whether any public route exists to make a *trusted* `<select>` option choice.** WebKit renders the popup as a native menu running a nested event loop; synthetic `NSEvent`s posted at the web view were not tested against it. Assume no until measured.
- **Whether a synthetic drag (`mouseDragged` sequences) is forwarded by WKWebView.** The `NSEventTypeMouseMoved` finding is documented; `NSEventTypeLeftMouseDragged` was not separately established. Do not state drag is blocked as a verified fact — state that the same class of forwarding gap applies and was not measured.
- **Whether `WKWebExtension`'s `webRequest` events actually flow for a host app's own web views**, and whether they work off macOS. Both flagged unresolved in the capability-ceiling document; prototype before publishing any network-observation capability claim.
- **The full tool list of Apple's `page_interactions`.** The shipped description names "click, type, keyPress, scroll, selectText, selectMenuItem, hover, highlightText" and the blog's says "click, type, scroll, hover, keyPress, etc." — the "etc." was never enumerated. Whether Apple can drag, right-click or answer a permission prompt is unknown.
- **Claude in Chrome's approval dialog wording** — whether it names the specific element, destination or value. Still the most important open question in the competitive picture, unchanged from the approval-landscape document.
- **Whether OpenAI's current built-in browser still cannot run code in the page.** The "cannot run code in the browser" wording is Atlas-era agent mode.
- **Gemini in Chrome's confirmation scope and whether it exposes JavaScript evaluation to the agent.** No Google-owned primary source found.
- **Comet's and Browser MCP's JavaScript-evaluation exposure.** Not stated either way by the vendor.
- **The hosted `mcp.browserbase.com` tool list**, which marketing still describes as including a screenshot tool the repository's own test file asserts absent. Needs an API key.
- **Whether `brainfuel/mcp-browser`, `Epistates/MCPSafari` or `achiya-automation/safari-mcp` reach selects, hover or dialogs specifically.** Their READMEs name eval, click, fill, submit, type, press_key and cookie tools; a per-operation enumeration was not obtained, and for `achiya-automation/safari-mcp` the tool count itself is disputed (97 in its README, 80 elsewhere).
- **Any measurement on this machine of the gaps in this document beyond the ones recorded as measured in the source and in `docs/research/2026-09-09-trusted-input-fidelity.md`.** This is a source-and-documentation audit; no browsing session was run for it.
