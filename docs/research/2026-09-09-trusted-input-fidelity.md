# Trusted input fidelity in browser automation: what is actually distinctive

Date: 2026-09-09

Question: Is dispatching a real AppKit `NSEvent` into a WKWebView a distinctive way to produce trusted DOM input, and is per-action measurement of `event.isTrusted` something any other automation tool does?

All URLs below were read on 2026-09-09.

---

## Verdict

**Native AppKit dispatch is not distinctive.** The W3C WebDriver specification *requires* every conformant driver to dispatch trusted events (`isTrusted == true`), explicitly names "sending operating system specific input messages to the browser's window" as one implementation strategy among several — and lists its disadvantages — and WebKit's own `safaridriver` already builds `NSEvent`s and delivers them with `[window sendEvent:]`, i.e. literally the technique this product describes ([WebDriver §15.4](https://w3c.github.io/webdriver/#ticks), [WebAutomationSessionMac.mm](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/Automation/mac/WebAutomationSessionMac.mm)).

**The measurement is distinctive, narrowly.** No mainstream driver returns a per-action trust field: WebDriver BiDi's `input.PerformActionsResult = EmptyResult`, WebDriver classic's Element Click returns null, and Playwright — the only tool found that reads `isTrusted` at all during an action — uses it as a filter inside its hit-target interceptor and then explicitly treats *the absence of any event* as success ("If we did not get any events, consider things working"), the opposite of failing indeterminate ([injectedScript.ts L1140-1168](https://raw.githubusercontent.com/microsoft/playwright/main/packages/injected/src/injectedScript.ts)).

**So the defensible claim is about the receipt contract, not the dispatch mechanism**, and it must not be extended into a claim of higher fidelity than CDP/WebDriver or into undetectability, since `navigator.webdriver` is spec-mandated for remote-controlled agents and trust is only the *input* to user activation, not what most gated APIs check.

### Adversarial summary of the table

CDP, WebDriver classic, WebDriver BiDi, `safaridriver`, Playwright and Puppeteer **all produce trusted events**. Trusted dispatch is table stakes; the WebDriver spec makes it a conformance requirement. Only JavaScript-level dispatch (`element.click()`, constructed events, `locator.dispatchEvent`) and Playwright's own WebView backend are untrusted.

Worse for the "native is better" framing, the WebDriver spec ranks the strategies and OS-level input is *not* the preferred one:

> "The most robust way to dispatch these events is by **creating them in the browser implementation itself**. Sending operating system specific input messages to the browser's window has the **disadvantage that the browser being automated may not be properly isolated from a user accidentally modifying an input source**. Use of an operating system level accessibility API has the disadvantage that the browser's window **must be focused**, and as a result, **multiple WebDriver instances cannot run in parallel**." — [WebDriver §15.4](https://w3c.github.io/webdriver/#ticks) (EXTERNAL-PRIMARY)

That focus/parallelism cost is real for this product too: WebKit's own implementation must call `[window makeKeyAndOrderFront:nil]` before every event batch.

## What `isTrusted` actually gates

The critical distinction: **almost nothing reads `isTrusted` directly.** `isTrusted` feeds *user activation*, and gated APIs check *transient activation*.

- **HTML user activation — the one place `isTrusted` is normative.** An "activation triggering input event" is an event "where the `isTrusted` attribute is **true**" and whose type is one of `keydown` (not Esc / reserved shortcut), `mousedown`, `pointerdown` (`pointerType == "mouse"`), `pointerup` (`pointerType != "mouse"`), `touchend`. Note that **`click` is not in the list** — an untrusted `mousedown` grants nothing regardless of what `click` looks like. [HTML §Tracking user activation](https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation) — EXTERNAL-PRIMARY
- **`Element.requestFullscreen()` — verified.** Step 5 requires "**this**'s relevant global object has **transient activation**" (or a user-generated orientation change); otherwise the promise rejects with `TypeError`. [Fullscreen API](https://fullscreen.spec.whatwg.org/#dom-element-requestfullscreen) — EXTERNAL-PRIMARY
- **`HTMLInputElement.showPicker()` — verified.** "Throws a `NotAllowedError` DOMException if called **without transient user activation**." (also `SecurityError` in a cross-origin iframe except File Upload / Color). [HTML §showPicker()](https://html.spec.whatwg.org/multipage/input.html#dom-input-showpicker) — EXTERNAL-PRIMARY
- **File input activation via `input.click()` — verified, but as a *vendor* behaviour, not a spec requirement.** HTML explicitly leaves it to UAs ("behaviors … triggered only by true user-initiated activations. A common choice is to show the picker"). Chromium implements it: `FileInputType` checks `if (!LocalFrame::HasTransientUserActivation(document.GetFrame()))` and logs `"File chooser dialog can only be shown with a user activation."` before returning without opening the picker. [file_input_type.cc L181-193](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/html/forms/file_input_type.cc) — EXTERNAL-PRIMARY (vendor source)
- **`PaymentRequest.show()` — verified, but only as a MAY.** Step 2: "If the relevant global object of *request* does not have **transient activation**, the user agent **MAY**: Return a promise rejected with a `SecurityError` DOMException." Step 3 consumes user activation. [Payment Request API](https://w3c.github.io/payment-request/#show-method) — EXTERNAL-PRIMARY
- **Clipboard — two different mechanisms, one of which names `trusted` directly.**
  - Async Clipboard API: "check clipboard read permission" and "check clipboard write permission" both begin "Let *hasGesture* be true if the relevant global object of **this** has **transient activation**"; write can be granted without a gesture via the `allowWithoutGesture: true` permission. [Clipboard API §9.1.1 / §9.2.1](https://w3c.github.io/clipboard-apis/#clipboard-permissions) — EXTERNAL-PRIMARY
  - `document.execCommand('copy'|'cut')`: "Copy and cut commands triggered through a scripting API will only affect the contents of the real clipboard if the event is dispatched from an event that is **trusted and triggered by the user**, or if the implementation is configured to allow this." [Clipboard API](https://w3c.github.io/clipboard-apis/) — EXTERNAL-PRIMARY
- **WebAuthn — verified, but far narrower than usually claimed.** `PublicKeyCredential.[[Create]]` requires transient activation **only when `sameOriginWithAncestors` is false** (i.e. cross-origin): "If the relevant global object … does not have **transient activation**: Throw a `NotAllowedError` DOMException. Consume user activation…". There is **no** occurrence of `isTrusted` or "user gesture" anywhere in the spec, and no activation requirement on `get()` or on same-origin `create()`. [WebAuthn Level 3 §5.1.3](https://w3c.github.io/webauthn/#sctn-createCredential) — EXTERNAL-PRIMARY
- **Autoplay with sound — vendor policy, not a spec, and not reducible to a gesture.** Chrome allows sound-on autoplay when "the user has interacted with the domain (click, tap, etc.)" **and/or** the Media Engagement Index threshold is met on desktop, or the site is installed. A single trusted click on a cold profile is therefore not sufficient. [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/) (page states "Last updated September 13, 2017") — EXTERNAL-PRIMARY (vendor docs)

### Commonly claimed, but NOT verified

- **`window.open` / popup allowance requires a trusted event or user activation.** **Not in the spec.** A full text scan of [HTML §Navigation and history APIs](https://html.spec.whatwg.org/multipage/nav-history-apis.html) found exactly one occurrence of "transient activation", and it concerns `location` history handling, not `window.open()`. The `open()` algorithm has no activation gate; popup blocking is unspecified UA behaviour. → UNAVAILABLE as a spec requirement.
- **WebAuthn / passkeys require a user gesture.** Not generally true — see above; only the cross-origin `create()` path. Could not verify any `isTrusted` requirement at all.
- **Clipboard *read* is gated on `isTrusted`.** It is gated on a permission whose check consults transient activation; `isTrusted` is not consulted.
- **Anything reads `event.isTrusted` at the API boundary.** Only the HTML activation definition and the Clipboard `execCommand` note do. Every other gate above reads *activation state*, which can be stale-but-valid (sticky) or expired (transient) independently of any single event's trust.
- **Apple's documented permission requirements for `CGEventPost`.** Page not retrievable (404s, see Unavailable).

## What this means for the product's claims

### Sentences that are safe to publish

1. "A confirmed click is delivered as a real AppKit `NSEvent` through AppKit event handling on the live `WKWebView`, so the page receives a trusted DOM event that grants transient user activation." — backed by [DOM](https://dom.spec.whatwg.org/#dom-event-istrusted), [HTML activation](https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation), [WebCore MouseEvent.h](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/dom/MouseEvent.h).
2. "`trusted_gesture_state` is not asserted from the dispatch path. It is set only when an isolated JavaScript receipt reports the matching DOM event with `isTrusted == true`; a missing or mismatched receipt makes the action fail indeterminate, and no trust flag is synthesised."
3. "Actions dispatched from page JavaScript — `element.click()`, a constructed `KeyboardEvent` — are reported untrusted, because the DOM standard initialises `isTrusted` to false for both." — [DOM](https://dom.spec.whatwg.org/#dom-event-istrusted).
4. "`confirmation_mode`, `dispatch_mode` and `trusted_gesture_state` are reported separately so that a caller can tell 'the human approved it', 'it was delivered natively', and 'the page confirmed a trusted event' apart, rather than inferring all three from one success boolean."
5. "No mainstream driver returns a per-action trust field: WebDriver classic's Element Click returns null, WebDriver BiDi defines `input.PerformActionsResult = EmptyResult`, and Playwright, which does read `isTrusted` internally for hit-target verification, treats the absence of any event as success." — [BiDi §7.9](https://w3c.github.io/webdriver-bidi/#module-input), [injectedScript.ts](https://raw.githubusercontent.com/microsoft/playwright/main/packages/injected/src/injectedScript.ts).

### Sentences that overreach — and how to reword them

| Overreaching | Why it fails | Reword to |
|---|---|---|
| "Unlike CDP or WebDriver automation, this dispatches *real* events." | CDP, WebDriver classic, BiDi, Playwright, Puppeteer and `safaridriver` all produce trusted events; WebDriver makes it a conformance requirement ([§15.4](https://w3c.github.io/webdriver/#ticks)). | "Like a conformant WebDriver driver, the dispatch produces trusted events. What differs is that trust is **verified per action and reported**, rather than assumed." |
| "Native AppKit dispatch is the highest-fidelity way to drive a WKWebView." | The WebDriver spec says the *most robust* way is creating events inside the browser implementation, and names concrete disadvantages of OS-level input (no isolation from stray user input; window must be focused; no parallel sessions). | "Native AppKit dispatch is one of the strategies the WebDriver specification names. It trades parallelism and isolation from stray user input for using the same entry point the OS uses." |
| "…through **public** AppKit event handling" (as an unqualified claim covering all gestures) | True for click/key via `[window sendEvent:]`, but WKWebView does **not** forward `NSEventTypeMouseMoved` to the underlying view; WebKit needed the private `_simulateMouseMove:` to make hover work at all. | Scope it: "Clicks and key events are delivered through public AppKit event handling. Mouse-move/hover is a known WKWebView gap (WebKit's own automation uses a private API for it) and is reported accordingly." |
| "A trusted gesture unlocks clipboard access, fullscreen, payment and passkeys." | Those APIs check **transient activation**, not `isTrusted`; `PaymentRequest` is a MAY; WebAuthn only gates cross-origin `create()`; clipboard write can be permission-granted without a gesture. | "A trusted `mousedown`/`keydown` grants transient user activation, which is what `requestFullscreen()`, `showPicker()`, `PaymentRequest.show()` and the clipboard permission checks consult." |
| "A trusted gesture makes the automation indistinguishable from a human." | The WebDriver spec's *own* wording is that the activation trigger is indistinguishable — the **session** is not: `navigator.webdriver` is spec-mandated, and CDP sessions are separately detectable. | "The DOM event is indistinguishable from a user's. Session-level automation signals are a separate matter and are not addressed by this flag." |
| "Trusted dispatch means popups and file pickers will work." | Popup allowance is unspecified; the file picker specifically depends on transient activation at the moment of activation, and native dialogs are out-of-page anyway (CDP and BiDi both had to add interception events for them). | "Trusted dispatch satisfies the transient-activation checks these features perform. Native OS dialogs are outside the page and are handled separately." |
| "No other tool measures trust." | Playwright's injected script does read `event.isTrusted` per action. | "No other tool **reports** trust to the caller, and Playwright — the only one that reads it — fails open when no event arrives, where this product fails indeterminate." |

### Question 4: detectability and gesture-failure cases

- **Spec-mandated detectability of any WebDriver session:** `navigator.webdriver` "Returns true if **webdriver-active flag** is set", the flag being "set to true when the user agent is under remote control" — [WebDriver §Interface](https://w3c.github.io/webdriver/#interface) — EXTERNAL-PRIMARY.
- **WebKit tags its own synthesized events:** `markEventAsSynthesizedForAutomation()` attaches an associated object to the `NSEvent`, with `event.eventNumber == 0` ("magic event number") as a fallback "for checking mouse events, which are frequently copied and/or faked by AppKit"; exposed to embedders as `-[_WKAutomationSession wasEventSynthesizedForAutomation:]` — [WebAutomationSessionMac.mm L77-155](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/Automation/mac/WebAutomationSessionMac.mm), [_WKAutomationSession.h](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/_WKAutomationSession.h) — EXTERNAL-PRIMARY. Trust and provenance are tracked separately even inside WebKit.
- **Documented case where OS-level dispatch fails where a real user succeeds:** automated mouse movement stopped producing DOM events in Safari after r290743 changed WKWebView to stop forwarding `NSEventTypeMouseMoved`; the fix required promoting `_simulateMouseMove:` to private API — [WebKit commit fc784f4](https://github.com/WebKit/WebKit/commit/fc784f4883874f8e3b50a861285d5396859fb4a1) — EXTERNAL-PRIMARY.
- **Documented case where synthesized input cannot reach native UI:** the file chooser. CDP: "When file chooser interception is enabled, **native file chooser dialog is not shown**. Instead, a protocol event `Page.fileChooserOpened` is emitted." — [CDP Page domain](https://chromedevtools.github.io/devtools-protocol/tot/Page/#event-fileChooserOpened). BiDi adds the same shape: `input.fileDialogOpened` / `input.setFiles` — [BiDi §7.9](https://w3c.github.io/webdriver-bidi/#module-input) — EXTERNAL-PRIMARY.
- **Trusted input still insufficient for autoplay-with-sound** on a cold profile, because Chrome additionally weighs the Media Engagement Index — [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/) — EXTERNAL-PRIMARY (vendor).
- **CDP-driven sessions are detectable independently of event trust** (the `Runtime.enable` console-preview side channel and related signals; reported as changed by two V8 commits in May 2025) — [DataDome threat research](https://datadome.co/threat-research/how-new-headless-chrome-the-cdp-signal-are-impacting-bot-detection/), [crawlex: CDP as a detection vector](https://blog.crawlex.net/blog/cdp-detection-vector/) — COMMUNITY-SIGNAL.
- **Untrusted synthetic events are a real, observed leak in agentic tooling:** browser-use issue #3829 "Synthetic Events Leak Automation with `isTrusted: true`" (2025-12-30) reports `default_action_watchdog.py` dispatching `new InputEvent()` / `new Event()`, i.e. untrusted; closed as *not planned* — [browser-use#3829](https://github.com/browser-use/browser-use/issues/3829) — COMMUNITY-SIGNAL. This is the useful comparison class for the product: agent frameworks, not test drivers.

## Unavailable

- **Apple's `CGEventPost` reference page** — both `https://developer.apple.com/documentation/coregraphics/cgeventpost(_:_:)` and `https://developer.apple.com/documentation/coregraphics/1541184-cgeventpost` returned HTTP 404 on 2026-09-09. The Accessibility/TCC permission requirement for cross-process event posting is therefore **uncited** here; do not assert it in product copy without a citation. (Note that the product's in-process `[window sendEvent:]` path does not need it — but that claim is also uncited.)
- **Apple's `safaridriver` developer documentation** (`https://developer.apple.com/documentation/webkit/testing-with-webdriver-in-safari`) returned only a title with no body through WebFetch; the `safaridriver` behaviour above is cited from WebKit source instead, which is stronger anyway.
- **A vendor statement from Google that CDP input is trusted.** The CDP reference does not say so. The claim rests on Chromium source (`input_handler.cc` → `RenderWidgetHostImpl::Forward*Event`) plus Puppeteer's FAQ, which is a Chrome-team-maintained document but not the protocol spec.
- **A normative statement anywhere that WebDriver BiDi events are trusted, written in the BiDi document itself.** The word "trusted" appears **zero** times in the BiDi spec; the requirement is inherited only by reference to WebDriver classic's *dispatch actions*.
- **Any per-action trust field in Selenium's or Playwright's public result payloads.** Searched the WebDriver/BiDi return types (`EmptyResult`) and Playwright/Puppeteer action APIs (void returns); none found. This is a negative finding from absence of evidence, not a positive citation.
- **A Chromium/WebKit source citation for popup-blocker activation checks.** Not retrieved; popup blocking remains unspecified in HTML and uncited here.
